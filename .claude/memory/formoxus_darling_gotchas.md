Hard-won while building [[formoxus_roadmap]]'s button system. Referenced from there; kept separate because these are reusable technical facts, not just "what we built."

**`Option<T>` fields never need `#[darling(default)]`.** Verified directly against the vendored `darling_core-0.24.0` source: when a field is absent from the attribute, darling calls that field type's `from_none()` rather than erroring (`codegen/field.rs` `CheckMissing`). `Option<T>`'s own `FromMeta` impl defines `from_none() -> Option<Self> { Some(None) }` — so a missing `#[form(title = ...)]` resolves to `None` with zero extra annotation. `#[darling(default)]` is only needed for non-`Option` types, or when you want a *non-`None`* fallback for an `Option` field.

**`Vec<T>` for a custom derived type needs `#[darling(multiple)]`, not a bare `Vec`.** darling only auto-implements `FromMeta for Vec<T>` for its own builtin literal/path types (`LitStr`, `Ident`, `Path`, etc.) — `Vec<ButtonInfo>` alone fails with "the trait bound `Vec<ButtonInfo>: FromMeta` is not satisfied". Fix: `#[darling(multiple, rename = "button")] pub buttons: Vec<ButtonInfo>` — this only requires `ButtonInfo: FromMeta` (not `Vec<ButtonInfo>: FromMeta`), and collects one element per repeated occurrence of an attribute with that name (`#[form(button(...))]` repeated, or combined in one `#[form(...)]` — darling merges nested items either way).

**`darling::util::SpannedValue<T>` captures the span of the meta item that produced a value.** Wrap the element type of a `#[darling(multiple)]` `Vec` in it (`Vec<SpannedValue<ButtonInfo>>`) to get, per element, `.span()` pointing at that specific `button(...)` occurrence — useful for `syn::Error::new(span, ...)` diagnostics that point at one bad button among several, not the whole derive. It `Deref`s to the inner `T`. Can't `impl SpannedValue<ButtonInfo> { ... }` directly (orphan rule — `SpannedValue` isn't a local type), so methods needing the span must take it as an explicit parameter (`fn text(&self, span: Span) -> TokenStream2`), threaded in by the caller who still has the `SpannedValue` wrapper.

**The recurring proc-macro mistake this session: confusing macro-expansion-time Rust with the generated code's runtime Rust.** Twice, code inside a `quote! { ... }` accidentally tried to *run* macro-local logic instead of *emitting tokens for* it:
- A literal `for btn in destructive.iter().chain(rest.iter()) { *btn.button_tokens(btn.span()) }` written directly inside `quote!{ rsx! { ... } }` with no `#`-splice — this doesn't iterate at derive-expansion time, it emits those exact identifiers (`destructive`, `rest`, `btn`, `.button_tokens`) as literal tokens into the *derived output*, which fails with `expected identifier` wherever `#[derive(Form)]` is actually used, since none of those exist in the user's crate at runtime. Fix: do the iteration as plain Rust *outside* `quote!` (`.map(...).collect::<Vec<TokenStream2>>()`), then splice the resulting list with `#(#tokens)*`.
- Nesting a full `rsx! { ... }` macro call inside another already-open `rsx! { ... }` by having a helper function's `quote!` wrap its own output in `rsx! { ... }`, then splicing *that* as a child of an outer `rsx! { form { ... } }`. rsx doesn't accept a raw macro-invocation token sequence as a child item. Fix: inner token-generating helpers (`ButtonInfo::button_tokens`, `FormMeta::tokens_for_buttons`) must emit bare element syntax (`button { ... }`, `div { ... }`) with no `rsx!` wrapper — only the single outermost `render()` body should actually invoke `rsx! { ... }`.
- Related attribute-syntax bug caught by the same pattern: `button { #r#type, #class, #text }` spliced all three as unlabeled bare children instead of `type`/`class` attributes — rsx attributes need `name: value` form (`button { r#type: #html_type, class: #class, #text }`); only the trailing text belongs as a bare child.

**Symptom to watch for:** `cargo check -p formoxus-macros` (the proc-macro crate itself) can pass clean even when the *emitted* code is completely broken, because `quote!`/darling don't validate the meaning of spliced tokens, only that the macro's own Rust compiles. The only real check is compiling something that actually uses `#[derive(Form)]` — `cargo check -p formoxus --tests` or `-p web --features server` — per the established verify-by-compiling habit in [[formoxus_roadmap]].

**Two more, hit while building the per-button-handler system (PR #9, 2026-08-22):**

- **A custom `#[darling(rename_all = "snake_case")]` unit-variant `FromMeta` enum only accepts a quoted string in `NameValue` position, not a bare path/ident** — `#[form(button(type = submit, ...))]` fails with `Unexpected type 'path'`; it must be `type = "submit"`. This is *specific to derived enums*: darling's own builtin `FromMeta` impls for `syn::Ident`/`syn::Path` (used for e.g. `name = submit`, `label_case = SomePath`) DO accept a bare path directly via a hand-written `from_expr` that matches `Expr::Path` — but the enum derive only generates `from_string`/`from_value`, no `from_expr` override, so a bare path never reaches the string-matching logic. Easy to get backwards: fields typed `syn::Ident`/`syn::Path` want bare idents; fields typed one of *your own* `FromMeta` enums want a quoted string.
- **A `quote!`-spliced RSX child that might be a plain function-call expression (not always a string literal) needs `{ #expr }` wrapping, not a bare `#expr`.** `button { r#type: #html_type, class: #class, #text }` worked while `#text` was always either a string literal or a `compile_error!()` macro invocation (rsx's parser special-cases macro calls in child position) — but once `text_tokens()` could also emit a real function call (`ToCase::to_case(name, label_case)`) for the no-explicit-`text` fallback, the *same* splice point broke with a bare `expected identifier` deep inside the `rsx!` expansion, no useful span. Diagnosed by `cargo expand`, which showed the failing `render()` body literally printed as `(/*ERROR*/)` — rsx silently gives up parsing a plain call as a bare child. Fix is the same brace-wrapping `field_meta.rs`'s `render_call` already used for its own (always-a-function-call) `render_expr` — worth defaulting to `{ #expr }` for *any* spliced rsx child whose tokens aren't unconditionally a literal, rather than relying on "it happened to work" from a narrower earlier case.
