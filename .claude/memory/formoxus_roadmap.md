Status as of `5cd1b40` (2026-08-22, `main`, pushed). Formoxus is a Dioxus 0.7 form library (`#[derive(Form)]` on a plain declaration struct) generalizing a pattern first hand-written for the login form. It's a sub-project inside the apcsp-dioxus workspace, not yet published standalone — Todd wants to publish it eventually, but deliberately deferred that: `formoxus`/`formoxus-macros` have zero dependency on the rest of the workspace today (same pattern as `surreal-table`/`surreal-table-macros`), so extraction stays a clean, easy split whenever it's actually useful to do.

**MVP tier — done:**
- `#[form(component = SomeWidget)]` per-field override (settled early — no separate `el` attribute).
- Full numeric widget coverage: u8..u128, i8..i128, usize/isize, f32/f64 — all render `type="text"` with `inputmode="numeric"`/`"decimal"` (not `type="number"`, to dodge cross-browser number-input inconsistencies; validation is unaffected, it's 100% Rust-side via `try_from::<T>` regardless of `type`). Built via `macro_rules!` + `paste!` in `crates/formoxus/src/widgets/number.rs`.
- Label/case system: `crates/formoxus/src/label_case.rs`'s `LabelCase` enum + `ToCase` trait. `#[form(label_case = ...)]` (form-level default) and `#[form(case = ...)]` (per-field override) take a **real `LabelCase` path expression**, not a string — chosen deliberately over darling's string+`FromMeta` approach for real IDE autocomplete/go-to-def, at the cost of losing darling's compile-time typo check (a normal Rust `E0599` covers most of that gap now). Precedence: field `case` > form `label_case` > default `Title`. An explicit `#[form(label = "...")]` renders verbatim UNLESS the same field also sets `case` (read as "yes, apply it to my custom text too"). Buttons deliberately share this same form-level `label_case` rather than getting their own `button_case` override — "we can think about that later" if it's ever actually needed.
- Form **title**: `#[form(title = "...")]` renders an `h2.form-title` above the form when set, nothing when not (`Option<String>` field on `FormMeta`, no `#[darling(default)]` needed — see [[formoxus_darling_gotchas]]).
- **Button system with per-button handlers (PR #9).** Every button — not just submit — gets its own async handler, wired to its `onclick` (or, for the submit button, the form's native `onsubmit`, so Enter-to-submit still works). Design:
  - `ButtonInfo { name: syn::Ident, ty: ButtonType, text: Option<String>, class: Option<String>, handler: Option<HandlerKind> }` — `name` is **mandatory** on every button (it's both the generated `Handlers` struct's field name and the local variable the generated closures capture/clone). `text` falls back to `ToCase::to_case(name, label_case)` when omitted, not a hardcoded per-`ButtonType` string — so `ButtonType::default_text()` was deleted outright as dead code.
  - `HandlerKind::{Validated, Unchecked}` — `Validated` runs `FormStoreExt::validate()` first and only calls the handler with `Some(model)`; `Unchecked` calls it unconditionally with no model, so `validate()`'s error-display side effect never fires. Defaulted per `ButtonType` (`Submit`/`Button` → `Validated`; `Cancel`/`Reset`/`Destructive` → `Unchecked`, since those need to work even on an invalid form) and overridable per-button via `handler = validated | unchecked`.
  - **Exactly one `type = submit` button is mandatory**, enforced in `FormMeta::validate()` — the old `submit_text`-driven auto-synthesis is gone entirely (deleted the field). A form that wants no *visible* submit button (a search box that submits on Enter) still needs one declared — HTML's implicit-submission mechanism routes Enter through the form's default submit button regardless, so there's no reliable submit-less path; the answer is a real submit button with a visually-hidden class, not a special no-button mode. (No `sr-only`/`visually-hidden` utility class exists in `main.scss` yet — add one whenever the first such form actually gets built.)
  - `FormState`/`FormStoreExt` gained `type Handlers` (the generated per-form struct) and `render` dropped its `on_submit`/generic-`F,Fut` parameter in favor of `render(data, handlers: Self::Handlers)`. New public API in `formoxus::form` (re-exported from `prelude`): `Handler<M>` / `UncheckedHandler` — `Rc<dyn Fn(...) -> Pin<Box<dyn Future<Output = ()>>>>` (`Rc`, not `Box`: the generated closures need to `.clone()` the handler into a fresh `async move` block on every click, and `Box<dyn Fn>` isn't `Clone`) — and `handler()`/`unchecked_handler()`, plain functions that wrap a caller's async closure so call sites never hand-write `Rc::new(|m| Box::pin(...))`.
  - `FormMeta::tokens_for_buttons()` partitions `Destructive` (rendered left-aligned) from everything else (right-aligned, sorted by `display_order()`: Reset, Cancel, Button, Submit), wrapping both in a single `div.formoxus-buttons`. Pico default classes: Submit→primary, Cancel→outline secondary, Button→secondary, Reset/Destructive→(outline) danger — Pico ships no real "danger" color itself, so that's a custom class the app's own CSS must define (not done yet). `.formoxus-buttons` in `crates/web/scss/main.scss` opts back out of Pico's forced `button[type=submit] { width: 100% }` (flex row, `justify-content: flex-end`) so it doesn't span the whole form.
  - `LoginForm`/`login.rs` and the hand-written `form_example.rs` spec (kept in sync deliberately, per its own doc comment) both updated to the new shape.
- SurrealDB dev environment on this machine: see [[surrealdb_dev_setup]] (unrelated to formoxus itself, but was fixed in an earlier session and blocks `dx serve` locally if missing).

**Done (2026-08-22, commit `5cd1b40`, pushed to `main`): forms crossing the server boundary, via `ChangePasswordForm`.** Migrating `change_password` (previously hand-written, no formoxus) off the old 3-string-arg `perform_password_change` surfaced a real architecture question with no prior memory of the answer — I initially guessed wrong (assumed `api` shouldn't depend on `formoxus`/Dioxus) before Todd corrected me and I checked `crates/api/Cargo.toml`: **`api` already deliberately depends on both `formoxus` and `dioxus` (`features = ["fullstack"]`)**, a prior decision undocumented anywhere I could find (see the lesson below). Landed shape:
  - **A form needing server-side validation lives in `api`, not `web`.** `web` depends on `api`, never the reverse, so only something defined in `api` (or lower) is visible to both a `#[post]` handler's signature and the `web` view rendering it. `ChangePasswordForm`/`#[derive(Form)]` now lives in `crates/api/src/auth.rs`; `web`'s `change_password.rs` just imports the generated `ChangePasswordForm`/`ChangePasswordFormState`/`ChangePasswordFormHandlers` from `api`. Generalizes past this one form: any form needing a `#[post]` handler to see its type belongs in `api`.
  - **The whole `…State` crosses the wire, in both directions** — not the model, not a hand-rolled error enum. `change_password(form_state: ChangePasswordFormState) -> ServerFnResult<Result<(), ChangePasswordFormState>>`: on success `Ok(Ok(()))`; on a server-discovered problem, `Ok(Err(form_state))` — the **same state type**, mutated with server-attached errors, sent straight back. The client (`submit_change_password` in `web`) does `*form.write() = form_state;` to replace its whole `Store` with what came back, so the same widgets show the same errors with zero enum-to-field translation layer. This retired the old `ChangePasswordError` enum entirely.
  - **Server-side re-validation is mandatory, never trust the client.** `perform_password_change` takes `mut form_state: ChangePasswordFormState` and calls `form_state.validate()` itself — the exact same generated method the client calls, plain data logic with no Dioxus dependency, so reusing it server-side needed no new code. Domain checks (old-password match, weak-password `zxcvbn`) run only after that succeeds, attaching errors via a new `FormField::add_error(&mut self, error_string: &str)` (`crates/formoxus/src/fields.rs`) when they fail.
  - **The generated `…State` struct now derives `Serialize`/`Deserialize`** (`form_state_struct` in `formoxus-macros/src/form.rs`) — needed for it to work as a server-fn param/return type at all. `FormField<T>`/`FieldValue<T>` already required both from every field type regardless (baked into their own derives), so this was additive, not structural, and doesn't newly constrain any existing form.
  - **Fixed-string server errors live in a new `api::messages` module** (`crates/api/src/messages.rs`, mirroring `web::messages`'s existing convention) so production code (`perform_password_change`, `check_new_and_confirm_match`) and the fixtures test assert against the same constant instead of duplicated literals. The dynamic weak-password reason (from `zxcvbn`'s `Display`) deliberately stays unasserted-on-exact-text in tests — just `not(is_empty())`.
  - **`crates/fixtures/tests/change_password.rs` migrated to googletest.** Async DB tests in this codebase use `#[tokio::test]` (need real `.await`), so use `assert_that!`, never `expect_that!` — the latter needs a `#[gtest]`-established "test context" to defer/aggregate failures into, which plain `#[tokio::test]` never sets up (fails at runtime with "No test context found", not a compile error — I made this exact mistake once before Todd caught it). `user_and_role_tests.rs` was already the working precedent for this.
  - **Two e2e tests/helpers needed updating** for the same reason `login`'s e2e helper already had to: formoxus's required-field marker (`" *"`) becomes part of a field's accessible name, so `get_by_label("Current Password", true)` (exact match) now needs `"Current Password *"`. `change_password`'s e2e helper predated that fix and wasn't caught until `just e2e` was actually run — worth remembering `cargo test`'s green doesn't cover this, only `just e2e` does.
- **Lesson for me, confirmed twice in one session — worth naming as a pattern, not just this one incident:** I asserted things without checking actual repo/runtime state first, twice: (1) "`api` shouldn't depend on `formoxus`" — reasoned from CLAUDE.md's crate-boundary prose instead of reading `Cargo.toml`; (2) reached for `expect_that!` from CLAUDE.md's general googletest guidance instead of checking how the *other* `#[tokio::test]`-based file in this exact crate already did it. Both times a one-command check (`cat Cargo.toml`, `grep` a sibling file) would have caught it before I said something wrong out loud. When a claim is checkable in one command, check it before asserting — especially anything about "should this crate depend on X" or "does this async-test pattern actually run here."

**MVP tier — next up (not started):**

- A "peek" handler shape (`Fn(Option<Model>) -> Fut`, always called) was discussed and deliberately deferred — it needs `validate()` split into a pure try-parse that doesn't mutate `data.errors`, a bigger internal change than the button system itself, and nothing concrete needs it yet.

**How this has been going, for a fresh session picking this up:** Todd writes the actual formoxus/formoxus-macros implementation himself (see [[user_role]]) and hands things to me to review + write tests once he has a version he's happy with — the loop each round has been: he writes/edits, asks "does this look okay, then write tests," I actually compile/run a real derived form (not just read the diff) to verify — this caught real bugs more than once (e.g. a `.to_case()` dot-call that only resolved because the test caller happened to `use formoxus::prelude::*;`, invisible from reading the code alone; and the `quote!`/`rsx!` nesting mistakes cataloged in [[formoxus_darling_gotchas]]). The button-handler rework (PR #9) was different: Todd talked through the whole design in conversation first before asking me to implement and open the PR myself, end to end. The change-password migration mixed both modes — Todd wrote/fixed most of `api/src/auth.rs` and the fixtures tests himself, handing me specific broken pieces ("check my errors," "take a look at the comments and figure out what I mean to do") rather than the whole thing at once. Worth staying flexible between "implement the whole thing" and "fix this specific piece" depending on how Todd frames the ask.
